# 응집도/결합도 & SOLID 원칙 체크리스트

## 높은 응집력(High Cohesion) 체크리스트

- [ ] 각 컴포넌트가 하나의 명확한 책임(기능적 목적)만 갖는가?
- [ ] 컴포넌트 내부 요소들이 그 책임을 위해 서로 밀접하게 협력하는가? (기능적으로 무관한 요소가 섞여 있지 않은가)
- [ ] 컴포넌트 이름이 그 책임을 한 문장으로 설명할 수 있는가? 설명에 "그리고/또는"이 여러 번 들어가면 응집도가 낮다는 신호입니다.

## 낮은 결합도(Low Coupling) 체크리스트

- [ ] 컴포넌트 간 의존이 실제로 필요한 상호작용에만 존재하는가? (불필요한 의존 제거)
- [ ] 의존이 구체 구현이 아니라 인터페이스/추상화를 향하고 있는가? (`references/interface-design.md` 참고)
- [ ] 순환 의존(A→B→A)이 없는가?
- [ ] 한 컴포넌트의 내부 변경이 다른 컴포넌트의 코드 변경 없이 흡수되는가? (인터페이스 계약을 깨지 않는 범위의 변경 기준)
- [ ] 공유 가변 상태(shared mutable state)를 통한 암묵적 결합이 없는가?

## SOLID 원칙 — 아키텍처 레벨 적용 체크리스트

| 원칙 | 아키텍처 레벨 의미 | 점검 질문 |
|---|---|---|
| SRP (단일 책임) | 컴포넌트는 하나의 변경 사유만 가져야 함 | 이 컴포넌트를 변경해야 하는 이해관계자/사유가 하나뿐인가? |
| OCP (개방-폐쇄) | 확장에는 열려있고 수정에는 닫혀있어야 함 | 새로운 변형(variant)을 추가할 때 기존 컴포넌트 내부를 수정하지 않고 인터페이스 구현 추가만으로 가능한가? |
| LSP (리스코프 치환) | 인터페이스의 구현체는 서로 치환 가능해야 함 | 동일 인터페이스의 다른 구현체로 교체해도 호출자 쪽 동작 가정이 깨지지 않는가? |
| ISP (인터페이스 분리) | 클라이언트가 쓰지 않는 기능에 의존하지 않아야 함 | 인터페이스가 너무 커서 일부만 쓰는 클라이언트가 강제로 전체에 의존하고 있지 않은가? |
| DIP (의존성 역전) | 상위 정책 모듈이 하위 구현 세부사항에 의존하지 않아야 함 | 상위 컴포넌트가 하위 컴포넌트의 구체 타입이 아니라 인터페이스에 의존하는가? |

각 원칙에 대해 "예/아니오"로만 답하지 말고, 이 아키텍처의 구체적인 컴포넌트/인터페이스를 근거로 제시하세요. 위반이 있으면 설계를 조정하거나, 불가피한 트레이드오프(예: 성능상 이유로 일부 결합 허용)라면 그 이유를 명시적으로 기록합니다.

## 변경 유연성 관점 추가 점검

- [ ] 요구사항 변경이 예상되는 지점(variation point)을 식별했는가? (예: 지원 하드웨어 추가, 알고리즘 교체, 규제 변경 대응)
- [ ] 각 variation point가 특정 컴포넌트/인터페이스 뒤에 격리되어 있어, 변경 시 영향 범위가 해당 컴포넌트로 한정되는가?
- [ ] 격리되지 않은 variation point가 있다면, 그로 인한 영향 범위를 명시하고 개선 여지를 기록했는가?
