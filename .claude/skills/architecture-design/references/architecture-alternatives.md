# 후보 아키텍처 구조 제안 절차

상세 설계 전에 반드시 수행합니다. 목적은 사용자가 트레이드오프를 이해하고 **직접 선택**하도록 하는 것입니다.

## 절차

1. §1(입력 파악)에서 얻은 설계 범위/제약(ASIL 유무, 변경 빈도가 예상되는 영역, 성능/자원 제약, 팀 구조 등)을 근거로, 아래 대표 스타일 중 이 문제에 적합한 2~4개를 선정합니다. 목록에 없는 스타일이 더 적합하면 자유롭게 제안하되 동일한 형식으로 설명합니다.
2. 각 후보에 대해: 핵심 아이디어, 이 프로젝트에 적용했을 때의 컴포넌트 분해 예시(간단한 다이어그램), 장점, 단점/리스크를 작성합니다.
3. 비교표를 만들어 아래 기준으로 각 후보를 평가합니다(상/중/하 또는 구체적 설명).
   - 응집도/결합도 확보 용이성
   - SOLID 원칙 적용 용이성
   - 변경 유연성(요구사항 변경 시 영향 범위)
   - ISO 26262 Part 6 적합성 (ASIL 분리/FFI 실현 가능성)
   - A-SPICE SYS.3/SWE.2 산출물 작성 난이도
   - 구현/통합 복잡도
4. `AskUserQuestion` 도구로 후보 목록을 제시하고 사용자가 하나를 선택하게 합니다(도구가 없는 컨텍스트라면 텍스트로 명확히 질문하고 응답을 기다립니다). **사용자 선택 없이 임의로 하나를 확정해 상세 설계를 진행하지 않습니다.**
5. 선택 결과와 선택 사유를 산출물의 "선택된 아키텍처 구조와 선택 사유"에 기록한 뒤 §3(상세 설계)으로 진행합니다.

## 대표 아키텍처 스타일 참고 목록

| 스타일 | 핵심 아이디어 | 강점 | 주의점 |
|---|---|---|---|
| 계층형(Layered) | 추상화 수준별로 계층을 나누고 상위→하위 단방향 의존만 허용 | 책임 분리가 명확, 하위 계층 재사용 용이 | 계층을 관통하는 기능(cross-cutting)이 많으면 결합도 증가 |
| 컴포넌트 기반(Component-Based, 예: AUTOSAR SWC 스타일) | 기능 단위를 컴포넌트로 캡슐화하고 포트/인터페이스로만 연결 | 인터페이스 기반 통신을 자연스럽게 강제, 재사용/교체 용이 | 컴포넌트 분해 기준을 잘못 잡으면 과도한 인터페이스 난립 |
| 이벤트 기반/발행-구독(Event-Driven / Pub-Sub) | 컴포넌트가 이벤트를 발행/구독하며 느슨하게 결합 | 결합도 최소화, 컴포넌트 추가/제거에 유연 | 이벤트 흐름 추적(디버깅)이 어려워질 수 있음, 타이밍 분석 필요(특히 안전 관련) |
| 파이프-필터(Pipe-and-Filter) | 데이터가 필터 컴포넌트를 순차 통과하며 변환 | 단계별 책임이 명확, 필터 단위 테스트 용이 | 상태를 공유해야 하는 경우 부적합, 양방향 상호작용 표현 어려움 |
| 마이크로커널/플러그인(Microkernel) | 핵심 기능과 확장 기능(플러그인)을 분리 | 핵심부 안정성 확보, 확장 기능 추가가 핵심부에 영향 없음 | 플러그인 간 상호작용이 필요하면 설계 복잡도 증가 |
| 클라이언트-서버 | 서비스 제공자(서버)와 요청자(클라이언트)로 역할 분리 | 책임 분리가 직관적 | 서버가 단일 실패점이 되지 않도록 안전 메커니즘 필요 |

안전 관련(ASIL) 요소가 섞여 있는 경우, 안전 요소와 비안전 요소를 분리해 배치할 수 있는 스타일(계층형, 컴포넌트 기반 + 파티셔닝)을 우선 고려하고, 그 근거를 FFI 관점에서 설명합니다.
