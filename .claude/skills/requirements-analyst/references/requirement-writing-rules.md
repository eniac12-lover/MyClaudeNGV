# 명확성(Clarity) & 일관성(Consistency) 작성 규칙

## EARS 패턴 (Easy Approach to Requirements Syntax)

모든 요구사항 서술은 아래 5가지 패턴 중 하나를 따릅니다. 패턴을 벗어난 자유 서술은 피하세요.

| 패턴 | 형식 | 사용 시점 |
|---|---|---|
| Ubiquitous(보편) | `<시스템>은 <응답>을 해야 한다.` | 항상 성립하는 요구 |
| Event-driven(이벤트) | `<트리거>가 발생하면, <시스템>은 <응답>을 해야 한다.` | 특정 이벤트에 대한 반응 |
| State-driven(상태) | `<상태>인 동안, <시스템>은 <응답>을 해야 한다.` | 특정 상태/모드에서만 유효 |
| Unwanted behavior(원치않는 동작) | `<원치않는 조건>이 발생하면, <시스템>은 <응답>을 해야 한다.` | 오류/예외/고장 대응(안전요구에 특히 중요) |
| Optional feature(선택 기능) | `<기능>이 포함된 경우, <시스템>은 <응답>을 해야 한다.` | 옵션 사양 |

여러 조건이 겹치면 위 패턴을 조합(Complex)하되, 문장을 나눠 원자성을 유지합니다.

## 명확성 체크리스트

- [ ] 요구사항 1건에 요구사항 1개만 있는가? ("~하고 ~한다", "~및 ~" 로 여러 요구가 묶여 있지 않은가)
- [ ] 의무 표현이 "~해야 한다(shall)"로 통일되어 있는가? (권고는 "~하는 것이 좋다(should)", 선택은 "~할 수 있다(may)"로 명확히 구분)
- [ ] 주어(대상 시스템/컴포넌트/기능)가 명시적인가? 수동태로 주체가 모호하지 않은가?
- [ ] 아래 금지 표현이 없는가? 있다면 정량적 기준으로 치환했는가?
  - "적절히", "충분히", "가능한 한", "필요시", "일반적으로", "빠르게", "안정적으로", "최대한", "즉시"(구체적 시간값 없이) 등
- [ ] 이 요구사항만 읽고 검증 담당자가 통과/실패를 판정할 수 있는가(정량적 acceptance criteria)?
- [ ] 약어/전문용어는 최초 등장 시 정의했거나 용어집에 있는가?

## 일관성 체크리스트 (신규/수정 요구사항마다 수행)

- [ ] 같은 개념에 다른 용어를 쓰고 있지 않은가? (기존 문서를 `Grep`으로 검색해 동의어 혼용 여부 확인)
- [ ] 수치/단위 표기가 문서 전체에서 동일한 형식인가? (예: ms/millisecond 혼용 금지, 소수점 표기 통일)
- [ ] 이 요구사항이 기존 요구사항과 같은 대상에 대해 다른 값·다른 동작을 요구하지 않는가? (모순 검토)
- [ ] ID 넘버링이 체계(`references/traceability.md`)를 따르고 중복이 없는가?
- [ ] 우선순위/ASIL/상태 등 메타데이터 표기 방식이 문서 전체에서 동일한가?
- [ ] EARS 패턴 선택이 유사한 성격의 다른 요구사항들과 일관되는가?

불일치를 발견하면 임의로 조용히 정정하지 말고, 무엇이 불일치했는지 사용자/리포트에 명시한 뒤 정정하세요.
