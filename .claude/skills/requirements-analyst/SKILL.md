# 요구사항 분석 스킬

ISO 26262, A-SPICE, ISO 25010을 준수하면서 **명확하고, 일관되고, 양방향 추적 가능한** 요구사항을 작성하기 위한 절차와 체크리스트입니다.

> 이 스킬의 체크리스트는 공개적으로 통용되는 표준 구조를 요약한 참고 자료입니다. 정확한 조항/문구는 실제 표준 원문과 대조하세요.

## 0. 템플릿 확인 (최우선)

이 프로젝트는 **지정된 요구사항 템플릿**을 반드시 준수해야 합니다 (`CLAUDE.md` "개발 생명 주기" 정책 참고).

1. 먼저 `references/requirement-template.md`를 읽습니다.
2. 그 파일 상단에 "TEMPLATE STATUS: PROVIDED"라고 표시되어 있으면 — 그 안의 템플릿을 **그대로** 따릅니다. 이 스킬의 다른 체크리스트(명확성, 일관성, 추적성, ISO 25010 등)는 템플릿의 각 필드를 채우는 방법을 안내하는 보조 자료로만 사용합니다.
3. 여전히 "TEMPLATE STATUS: PENDING"이면 — 사용자가 아직 템플릿을 제공하지 않은 것입니다. 이 경우:
   - `references/requirement-template.md`에 있는 **기본 임시 템플릿**을 사용해 작업을 진행합니다(작업을 멈추지 않습니다).
   - 산출물 상단에 "⚠️ 사용자 지정 템플릿 미제공 — 기본 템플릿 사용 중. 템플릿 제공 시 재구성 필요"라고 명시합니다.
   - 사용자가 나중에 템플릿을 제공하면, `references/requirement-template.md`를 그 내용으로 교체(상태를 PROVIDED로 변경)하고, 기존에 기본 템플릿으로 작성된 요구사항들을 새 템플릿 형식으로 재작성할 것을 제안합니다.

## 1. 명확성(Clarity) 확보

`references/requirement-writing-rules.md`의 EARS 패턴과 금지 표현 목록을 따라 작성합니다. 핵심 원칙:
- 요구사항 1건 = 요구사항 1개 (원자성). "그리고/또는"으로 여러 요구를 묶지 않습니다.
- 모호한 수식어("적절히", "충분히", "가능한 한", "빠르게" 등) 금지 — 측정 가능한 기준으로 치환합니다.
- 의무 표현은 "~해야 한다(shall)"로 통일하고, 권고/선택 사항과 표현을 구분합니다.
- 대상(주어)을 명확히 하고 능동태로 작성합니다.

## 2. 일관성(Consistency) 확보

`references/requirement-writing-rules.md`의 일관성 체크리스트를 따릅니다. 새 요구사항을 추가/수정할 때마다:
- 기존 요구사항 문서를 `Grep`으로 검색해 동일/유사 개념에 다른 용어를 쓰고 있지 않은지 확인하고, 있으면 용어집(Glossary)에 등록된 용어로 통일합니다.
- 수치/단위 표기가 문서 전체에서 일관된지 확인합니다.
- 새 요구사항이 기존 요구사항과 모순(동일 대상에 다른 값/동작 요구)되지 않는지 교차 검토합니다.
- ID 체계, 문장 패턴(EARS), 우선순위/ASIL 표기 방식이 문서 전체에서 동일한지 확인합니다.
- 발견된 불일치는 조용히 고치지 말고 사용자에게 보고한 뒤 정정합니다.

## 3. 기능 요구사항(FR) — UML/SysML 다이어그램

`references/functional-requirements-uml-sysml.md`를 참고해, 요구사항의 성격에 맞는 다이어그램을 Mermaid로 함께 제공합니다(별도 툴 설치 없이 렌더링 가능).
- 액터-시스템 상호작용 → Use Case Diagram
- 처리 흐름/알고리즘 → Activity Diagram
- 시간에 따른 컴포넌트 간 메시지 교환 → Sequence Diagram
- 모드/상태 의존 동작 → State Machine Diagram
- 시스템 구조/구성요소 관계 → SysML Block Definition Diagram(class diagram으로 근사 표현)
- 요구사항 간 관계(derive/satisfy/verify) → SysML Requirement Diagram(근사 표현, 관계 표에 명시)

## 4. 비기능 요구사항(NFR) — ISO 25010 + 실행 가능한 검증방안

`references/nfr-iso25010.md`의 품질 특성표를 사용해 각 NFR을 하나의 ISO 25010 (하위)특성에 매핑하고, 다음을 함께 작성합니다.
- 측정 가능한 목표치(metric + target value)
- **실행 가능한** 검증 방안(구체적 절차/도구/합격기준). "적절히 테스트한다", "충분히 검토한다" 같은 실행 불가능한 표현은 금지합니다. 실행 가능 여부가 불확실하면 실제로 그 방법을 수행할 수 있는지 스스로 검토한 후 제시하세요.

## 5. ISO 26262 / A-SPICE 정합성

`references/iso26262-aspice-mapping.md`를 참고해 안전 관련 요구사항에는 ASIL, 안전목표(Safety Goal) 연계, FSR/TSR 구분 등 필요한 속성을 포함시키고, A-SPICE SYS.1/SYS.2/SWE.1의 산출물 기대사항(검증기준 포함, 추적성 등)을 만족시킵니다.

## 6. 양방향 추적성(Traceability) 유지

`references/traceability.md`의 ID 체계와 추적성 매트릭스 형식을 사용합니다.
- 모든 요구사항에 규정된 접두어(STR/SR/NFR/SG/FSR/TSR/SWR 등)로 시작하는 고유 ID를 부여합니다.
- 요구사항을 생성/수정할 때마다 공식 추적성 매트릭스(`WP_Templates/Engineering/Traceability/TPL-TRC-001_...xlsx`, `references/traceability.md` §0)를 함께 갱신합니다. 매트릭스 갱신을 잊지 마세요 — 요구사항 작성과 별개 작업이 아니라 하나의 완료 조건입니다.
- 상위(이해관계자 요구/안전목표) → 하위(설계/코드/테스트) 방향과, 하위 → 상위 방향 모두 확인할 수 있어야 합니다(고아 요구사항·미검증 요구사항이 없는지 주기적으로 점검).

## 7. 출력

산출물은 §0에서 확인한 템플릿(제공되었으면 그 템플릿, 아니면 기본 템플릿)을 따르고, 위 5개 관점(명확성/일관성/다이어그램/ISO25010 검증방안/추적성)을 모두 충족했는지 마지막에 자체 점검 목록으로 요약해 사용자에게 보고합니다.
