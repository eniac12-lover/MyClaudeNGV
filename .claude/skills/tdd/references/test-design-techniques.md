# 테스트 설계 기법 카탈로그 (프로젝트 공용)

> **이 파일은 이 프로젝트의 유일한 테스트 설계 기법 카탈로그입니다.** `tdd`(단위), `integration-test`(SWE.5 통합), `sw-system-test`(SWE.6 시스템) 스킬이 모두 이 파일을 참조합니다 — 각 스킬이 기법 목록을 별도로 다시 정의하지 않습니다.

`CLAUDE.md` "참고 자료"가 인용하는 **ISO 29119**(동적 SW 테스팅 표준)/ISTQB 계열에서 통용되는 테스트 설계 기법을 요약한 것입니다. 테스트 케이스/함수의 `기법`(`Technique`/`@technique`) 항목에는 아래 목록 중 실제로 적용한 기법을 명시합니다(정확한 조항/정의는 표준 원문과 대조하세요).

| 기법 | 설명 | 적용 시점 |
|---|---|---|
| 동등분할 (Equivalence Partitioning) | 입력값을 "같은 방식으로 처리될 것으로 기대되는" 클래스로 나누고, 클래스마다 대표값 하나씩 테스트 | 입력 유효성 검증, 값의 범위/카테고리에 따라 동작이 달라질 때 |
| 경계값 분석 (Boundary Value Analysis) | 유효/무효 구간의 경계(최소, 최대, 경계 바로 안/밖)를 테스트 | 숫자/길이 등 범위 제약이 있는 입력 |
| 결정 테이블 테스트 (Decision Table Testing) | 여러 조건의 조합과 그에 따른 기대 동작을 표로 정리해 각 조합을 테스트 | `detailed-design` §7 정책 의사결정표가 있는 로직 |
| 상태 전이 테스트 (State Transition Testing) | 상태-이벤트-전이 조합을 테스트(유효 전이, 무효 전이 모두) | `detailed-design` §8 상태전이 상세가 있는 컴포넌트 |
| 분류 트리 (Classification Tree) | 입력 조건을 트리 구조로 분류하고 조합을 선택해 테스트 | 입력 파라미터가 많고 조합 폭발이 우려될 때 |
| 전수 조합 테스트 (Exhaustive Combinatorial Testing) | 관련 조건들의 **모든** 조합을 생성해 테스트 | 관련 조건 수가 적어 전수 조합이 실행 가능한 범위일 때 |
| 페어와이즈 테스트 (Pairwise Testing) | 전수 조합 대신, 모든 파라미터 쌍(pair)의 조합을 커버하는 최소 조합만 선택 | 조건·값 조합 수가 많아 전수 조합이 비현실적일 때 |
| 구문 기반 테스트 (Syntax Testing) | 입력 형식(포맷/프로토콜/문법) 규칙 위반 케이스를 체계적으로 생성 | API/파일 포맷 파싱, 입력 검증 로직 |
| 경험 기반 테스트 (Experience-based Testing: 오류 추측/탐색적 테스트) | 유사 시스템의 결함 이력이나 QA 경험에 근거해 실패하기 쉬운 케이스(널, 빈 값, 특수문자, 동시성, 극단적 조건 등)를 추정 | 다른 기법으로 커버되지 않는 경험 기반 보완, 명세가 불충분한 영역 |
| 체크리스트 기반 테스트 (Checklist-based Testing) | 조직/도메인의 체크리스트 항목을 그대로 테스트 케이스화 | 코딩/보안 표준 준수 확인 |

## 전수 조합 / 페어와이즈 도구 — PICT (오픈소스)

조건·값의 조합이 여러 개 얽힌 케이스는 손으로 나열하지 말고 오픈소스 도구 [PICT](https://github.com/microsoft/pict)로 생성합니다.

- **페어와이즈(기본)**: `pict <모델파일>` — 모든 조건 쌍을 커버하는 최소 조합을 생성합니다.
- **전수 조합**: `pict <모델파일> /o:max` — 관련 조건의 모든 조합을 생성합니다(조건 수가 적을 때만 사용 — 조합 폭발 주의).
- 모델 파일은 파라미터와 그 값 목록을 정의한 텍스트 파일입니다(PICT 문서 형식 참고). 생성된 각 조합 행이 테스트 케이스 하나가 됩니다.

## 긍정(Positive)/부정(Negative) 케이스 구분

- **Positive(긍정)**: 유효한 입력·정상 경로에서 기대되는 동작을 검증(계약의 사후조건이 성립함을 확인).
- **Negative(부정)**: 유효하지 않은 입력, 예외 상황, 계약 위반 시도, 경계 바깥 값 등에서 시스템이 올바르게 거부/오류처리/방어하는지 검증(계약의 사전조건 위반 시 동작, 예외 처리를 확인).

하나의 함수 계약을 커버할 때, 최소한 **Positive 1건 이상 + 관련 Negative 케이스(예외/경계마다 1건 이상)**를 작성하는 것을 기본으로 합니다. 부정 케이스가 없으면 `tdd` 스킬의 완료 체크리스트에서 누락으로 보고합니다.
