# 테스트 설계 기법 카탈로그 (`@technique` 태그용)

`CLAUDE.md` "참고 자료"가 인용하는 **ISO 29119**(동적 SW 테스팅 표준) 계열에서 통용되는 테스트 설계 기법을 요약한 것입니다. 테스트 함수의 Doxygen 주석 `@technique` 태그에는 아래 목록 중 이 테스트에 실제로 적용한 기법을 명시합니다(정확한 조항/정의는 표준 원문과 대조하세요).

| 기법 | 설명 | 적용 시점 |
|---|---|---|
| 동등분할 (Equivalence Partitioning) | 입력값을 "같은 방식으로 처리될 것으로 기대되는" 클래스로 나누고, 클래스마다 대표값 하나씩 테스트 | 입력 유효성 검증, 값의 범위/카테고리에 따라 동작이 달라질 때 |
| 경계값 분석 (Boundary Value Analysis) | 유효/무효 구간의 경계(최소, 최대, 경계 바로 안/밖)를 테스트 | 숫자/길이 등 범위 제약이 있는 입력 |
| 결정 테이블 테스트 (Decision Table Testing) | 여러 조건의 조합과 그에 따른 기대 동작을 표로 정리해 각 조합을 테스트 | `detailed-design` §7 정책 의사결정표가 있는 로직 |
| 상태 전이 테스트 (State Transition Testing) | 상태-이벤트-전이 조합을 테스트(유효 전이, 무효 전이 모두) | `detailed-design` §8 상태전이 상세가 있는 컴포넌트 |
| 분류 트리 (Classification Tree) | 입력 조건을 트리 구조로 분류하고 조합을 선택해 테스트 | 입력 파라미터가 많고 조합 폭발이 우려될 때 |
| 페어와이즈/조합 테스트 (Combinatorial/Pairwise Testing) | 모든 조합 대신 파라미터 쌍 조합을 커버하는 최소 조합 선택 | 파라미터 조합이 매우 많아 전수 테스트가 비현실적일 때 |
| 구문 기반 테스트 (Syntax Testing) | 입력 형식(포맷/프로토콜/문법) 규칙 위반 케이스를 체계적으로 생성 | API/파일 포맷 파싱, 입력 검증 로직 |
| 오류 추측 (Error Guessing) | 경험적으로 실패하기 쉬운 케이스(널, 빈 값, 특수문자, 동시성 등)를 추측해 테스트 | 다른 기법으로 커버되지 않는 경험 기반 보완 |
| 체크리스트 기반 테스트 (Checklist-based Testing) | 조직/도메인의 체크리스트 항목을 그대로 테스트 케이스화 | 코딩/보안 표준 준수 확인 |

## 긍정(Positive)/부정(Negative) 케이스 구분

- **Positive(긍정)**: 유효한 입력·정상 경로에서 기대되는 동작을 검증(계약의 사후조건이 성립함을 확인).
- **Negative(부정)**: 유효하지 않은 입력, 예외 상황, 계약 위반 시도, 경계 바깥 값 등에서 시스템이 올바르게 거부/오류처리/방어하는지 검증(계약의 사전조건 위반 시 동작, 예외 처리를 확인).

하나의 함수 계약을 커버할 때, 최소한 **Positive 1건 이상 + 관련 Negative 케이스(예외/경계마다 1건 이상)**를 작성하는 것을 기본으로 합니다. 부정 케이스가 없으면 `tdd` 스킬의 완료 체크리스트에서 누락으로 보고합니다.
