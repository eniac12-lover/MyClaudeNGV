# 좋은 테스트 작성하기

출처: [obra/superpowers](https://github.com/obra/superpowers) `skills/test-driven-development/writing-good-tests.md`를 Python/`unittest` 기준으로 번역·적용.

**언제 참고하는가:** 테스트를 작성/수정할 때, 모킹을 추가할 때, 테스트용 정리(cleanup)/헬퍼 메서드를 추가할 때.

## 개요

테스트는 특정한 "깨짐"을 잡기 위해 존재합니다. 두 가지 원칙이 모든 것을 지배합니다.

```
1. 모든 테스트는 자신이 잡는 깨짐을 이름/주석으로 밝힌다 (이 프로젝트에서는 @brief/@technique/@case)
2. 모든 테스트는 진짜 코드를 실행한다
```
엄격한 TDD(§Red 확인을 반드시 수행)를 따르면 이 두 가지는 자연스럽게 달성됩니다 — 실제 코드에 대해 먼저 실패를 확인한 테스트는 이미 "깨질 수 있음"을 증명한 것이고, 느리거나 외부 의존적인 대상일 때만 모킹할 가치가 생깁니다.

## 원칙 1: 깨짐을 이름으로 밝힌다

테스트 본문을 쓰기 전에 답하세요: **어떤 프로덕션 코드 변경이 이 테스트를 실패하게 만드는가 — 그리고 그 변경은 버그인가, 설계 결정인가?** 테스트는 잘못된 분기, 누락된 부작용, 잘못된 인자, 경계 케이스, 깨진 계약 중 하나를 잡을 때 존재 가치가 있습니다.

**기대값은 독립적으로 도출합니다.** 리터럴 값과 직접 검산한 픽스처를 사용하세요. 검증 대상 코드(또는 그 헬퍼)로 계산한 기대값은 그 코드가 무엇을 하든 항상 통과합니다.

```python
# ❌ 거울 단언(mirror assertion): 같은 함수로 양쪽을 계산 — 항상 참
expected = buildSearchQuery({"tag": "urgent"})
self.assertEqual(buildSearchQuery({"tag": "urgent"}), expected)

# ✅ 직접 계산한 리터럴
self.assertEqual(buildSearchQuery({"tag": "urgent"}), 'tag:"urgent"')
```

**변경 감지기(change detector)를 만들지 않습니다.** 의도적인 설계 결정만 실패시키는 테스트(상수값, 정확한 메시지 문구, 내부 구조)는 재설계 때마다 울리고 실제 버그에는 잠들어 있습니다. 결정 자체가 아니라 그 결정에 의존하는 **동작**을 테스트하세요: `self.assertEqual(MAX_RETRIES, 5)`가 아니라 "실패한 호출이 5번 재시도되고 6번째 시도는 일어나지 않는다"를 검증합니다.

**동작을 테스트하지, 텍스트를 테스트하지 않습니다.** 스크립트/설정 파일이 특정 줄을 포함하는지 확인하는 것은 소스가 소스라는 것만 증명합니다. 스크립트는 통제된 입력으로 실행해 출력/부작용/종료 코드를 검증하세요.

**여러분의 코드를, 프레임워크가 아니라 테스트합니다.** 코드가 경계에서 맺는 계약(등록하는 라우트, 만드는 쿼리, 생성하는 payload)을 테스트하세요. 업스트림(표준 라이브러리, 프레임워크)의 동작은 그쪽 유지보수자의 테스트 몫입니다. 업스트림 동작이 예상과 달라 실제로 놀랐던 적이 있다면, 그 가정을 명시한 좁은 범위의 특성화 테스트(characterization test) 하나만 작성하세요.

### 게이트 함수

```
테스트 본문을 쓰기 전에:
  이 테스트를 실패시킬 프로덕션 코드 변경을 말할 수 있는가?

  말할 수 없다 → 관찰 가능한 동작 중심으로 다시 설계
  "소스 텍스트가 바뀌면 실패한다" → 산출물을 실행해서 효과를 검증하도록 변경
  의도적 설계 결정만 잡아낸다 → 변경 감지기임. 그 결정에 의존하는 동작을 테스트

  기대값이 검증 대상 코드 없이 도출되었는지 확인한다.
  검증 대상 코드/헬퍼를 재사용해 계산했다면:
    리터럴이나 직접 검산한 픽스처로 교체한다
```

## 원칙 2: 진짜 코드를 실행한다

**모킹 자체는 아무것도 증명하지 않습니다.** 모킹에 대한 단언은 모킹이 존재하면 통과하고 없으면 실패할 뿐, 실제 컴포넌트에 대해서는 아무것도 말해주지 않습니다. 실제 컴포넌트의 동작을 단언하세요. 모킹 자체를 검증하고 있다면, 모킹을 풀거나 그 단언을 지우세요.

```python
# ✅ 실제 동작 검증
self.assertTrue(routeExists(app, "/api/users"))

# ❌ 모킹의 존재만 검증
self.assertTrue(mock_sidebar.called)
```

**적절한 수준에서 모킹합니다.** 실제 메서드의 모든 부작용을 파악한 뒤, 느리거나 외부적인 연산만 대체하고 테스트가 의존하는 부분은 실제로 남겨둡니다. 확신이 없으면 먼저 실제 구현으로 테스트를 실행해 무엇이 실제로 필요한지 관찰하세요.

```python
# ❌ 모킹이 중복 감지 로직이 읽는 설정 쓰기까지 삼켜버림
@patch("myapp.tool_catalog.discover_and_cache_tools", return_value=None)
def test_x(self, mock_discover):
    ...

# ✅ 느린 서버 기동만 모킹, 설정 쓰기는 실제로 수행됨
@patch("myapp.mcp_server_manager.MCPServerManager")
def test_x(self, mock_manager):
    ...
```

**더블(mock/stub/fake)은 구체적으로 만듭니다.** 인자, 호출 횟수, 순서가 계약의 일부라면 그것을 단언하세요. 무엇이든 받아주는 페이크는 아무것도 검증하지 못합니다. 성공/오류/잘못된 입력 각 분기마다 별도의 픽스처나 스파이를 둡니다.

**모킹 데이터는 실제 구조를 완전히 반영합니다.** 테스트가 읽는 필드만이 아니라 실제로 존재하는 전체 문서화된 필드를 모킹하세요. 부분 모킹은 다운스트림 코드가 누락된 필드를 읽을 때 조용히 실패합니다 — 테스트는 통과하는데 실제 통합은 깨집니다.

**프로덕션 클래스에는 프로덕션 메서드만 둡니다.** 테스트만 필요로 하는 정리(cleanup) 코드는 프로덕션 클래스의 `destroy()` 같은 메서드가 아니라 테스트 유틸리티에 둡니다.

**모킹이 복잡해지면 실제 컴포넌트를 쓰는 통합 테스트로 전환합니다.** 모킹 설정이 테스트 로직보다 커지거나, 실제 컴포넌트에는 있는 메서드가 모킹에는 없거나, 모킹이 바뀔 때마다 테스트가 깨진다면 신호입니다.

### 게이트 함수

```
모킹이나 테스트 헬퍼를 추가하기 전에:
  실제 메서드의 부작용을 나열하고, 테스트가 의존하는 것은 실제로 남긴다
  — 느리거나 외부적인 수준만 모킹한다.

  모킹 응답은 실제 구조를 완전히 반영한다.

  테스트만 호출하는 메서드는 테스트 유틸리티에 둔다(프로덕션 클래스 아님).

  지금 모킹 자체를 단언하려는가?
    모킹을 풀거나 그 단언을 지운다.
```

## 테스트는 구현과 함께 완성된다

TDD 사이클(실패하는 테스트 → 최소 구현 → 리팩터링)이 곧 "완료"의 정의입니다. 그 동작이 필요로 하는 테스트만 남기세요 — 사소한 코드와 사람이 읽는 산문(설명 문서 등)은 테스트가 필요 없고, 오직 프로세스를 만족시키기 위해 쓴 테스트는 유지보수 비용만 영원히 남깁니다.

## 뮤테이션 체크

끝내기 전에 프로덕션 코드를 머릿속으로 "변조(mutate)"해 보세요. 현실적인 변조마다 최소 하나의 테스트가 실패해야 합니다.

- 잘못된 상수/인자
- 잘못된 분기 처리
- 누락된 상태 변경/부작용
- 빈 값 또는 기본값 반환
- 0/빈 값/None/권한없음/잘못된 형식 입력에 대한 검증 누락

어떤 변조도 잡아내지 못하는 테스트가 있다면, 그 동작은 보호되지 않고 있거나 그 테스트가 동어반복(tautology)이라는 뜻입니다.

## 빠른 참고

| 상황 | 할 일 |
|---|---|
| 아무 테스트나 작성할 때 | 그것이 잡는 깨짐을 밝힌다 — 설계 결정이 아니라 버그 |
| 기대값을 만들 때 | 직접 도출한다. 검증 대상 코드로 계산하지 않는다 |
| 스크립트/문서를 테스트할 때 | 실행해서 효과를 검증한다. 텍스트를 grep하지 않는다 |
| 의존성(표준 라이브러리 등)을 테스트하고 싶을 때 | 여러분 코드의 경계 계약을 테스트한다 |
| 모킹된 요소를 단언하고 싶을 때 | 실제 컴포넌트를 테스트하거나 모킹을 푼다 |
| 메서드를 모킹하려 할 때 | 부작용을 파악하고 느리거나 외부적인 수준만 모킹한다 |
| 모킹 응답을 만들 때 | 실제 구조를 완전히 반영한다 |
| 테스트에만 필요한 정리 코드가 필요할 때 | 테스트 유틸리티에 둔다 |
| 모킹 설정이 비대해질 때 | 실제 컴포넌트를 쓰는 통합 테스트로 전환한다 |
| 테스트 파일을 끝낼 때 | 뮤테이션 체크를 수행한다 |

## 경고 신호

- 준비(setup)와 단언이 같은 객체를 사용해 항상 같음을 보장함
- 예외/크래시/셀렉터 실패로만 테스트가 실패할 수 있음
- 의도적 변경마다 실패하고 실제 버그에는 절대 실패하지 않음
- 기대값이 반복문/빌더/헬퍼 뒤에 숨겨져 있음
- 소스 텍스트를 grep하거나, 제거된 심볼이 계속 없는지만 확인함
- 프레임워크만 남아도 여전히 의미가 있는 테스트임(즉 여러분 코드를 전혀 검증하지 않음)
- 커버리지를 채우기 위해서만 존재하고 부작용/결과를 확인하지 않음
- `*-mock`류의 테스트 ID를 단언하거나, 모킹을 제거하면 실패함
- 어떤 메서드가 테스트 파일에서만 호출됨
- 모킹 설정이 테스트의 절반 이상을 차지하거나, 왜 그 모킹이 필요한지 설명할 수 없음
- "혹시 몰라서" 모킹함
