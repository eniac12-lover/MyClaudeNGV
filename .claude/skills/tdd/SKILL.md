# TDD 스킬 (Red-Green-Refactor)

출처: [obra/superpowers](https://github.com/obra/superpowers) `skills/test-driven-development`를 이 프로젝트(Python 3.14, `unittest`, `detailed-design`/`coding` 스킬 체계)에 맞게 번역·적용한 버전입니다. 이 스킬은 개발 방법론만 다루며, 코드 품질 지표(라인수/복잡도/중복/주석/네이밍)는 `coding` 스킬이 별도로 강제합니다 — 이 스킬은 그 세부 수치를 재정의하지 않습니다.

## 핵심 원칙

**테스트를 먼저 작성한다. 실패하는 것을 직접 확인한다. 통과시키는 최소한의 코드를 작성한다.**

> "테스트가 실패하는 것을 직접 보지 않았다면, 그 테스트가 올바른 것을 검증하는지 알 수 없다."

**규칙의 문구를 어기는 것은 규칙의 취지를 어기는 것과 같습니다.** "이번만 TDD를 건너뛰자"는 생각이 든다면, 그것은 규칙을 피하려는 합리화입니다 — 멈추세요.

## 언제 적용하는가

**항상 적용:** 신규 기능, 버그 수정, 리팩터링, 동작 변경.

**예외(사용자에게 먼저 확인):** 일회성 프로토타입, (사람이 아닌 도구가 생성하는) 생성 코드, 설정 파일.

## 철칙(Iron Law)

```
실패하는 테스트 없이는 프로덕션 코드를 작성하지 않는다.
```

테스트보다 먼저 코드를 작성했다면 — **삭제하고 다시 시작합니다.**
- "참고용"으로 남겨두지 않습니다
- 테스트를 작성하면서 그 코드를 "조금씩 다듬어" 재사용하지 않습니다
- 쳐다보지 않습니다
- 삭제는 삭제입니다 — 테스트로부터 처음부터 새로 구현합니다

## 0. 입력 확인 (이 프로젝트 고유 단계)

`detailed-design` 산출물의 함수 계약(입력/출력/사전조건/사후조건/예외, `detailed-design`의 `references/function-contracts-and-algorithms.md` 형식)을 확인합니다. 계약이 없으면 사용자에게 확인합니다 — 계약 없이 테스트를 임의로 지어내지 않습니다. 계약의 각 사전조건/사후조건/예외/경계값이 곧 이후 작성할 테스트 목록이 됩니다.

## Red-Green-Refactor 사이클

### 1. RED — 실패하는 테스트 작성

이번에 검증할 동작 하나만 다루는 최소한의 테스트를 작성합니다.

- 한 테스트는 한 가지 동작만 검증합니다(이름에 "그리고/and"가 필요하면 테스트를 나눕니다).
- 이름은 시나리오를 설명해야 합니다(예: `test_returnsErrorWhenEmailIsEmpty`, camelCase 3글자 이상 — `coding`의 `references/naming-conventions.md`와 동일 규칙).
- 실제 코드를 검증해야 합니다 — 모킹 대상 자체의 동작을 검증하는 테스트를 만들지 않습니다(`references/writing-good-tests.md` 참고).
- 이 테스트에 **§테스트 함수 주석 규칙**(아래)에 따라 목적/기법/긍정·부정 여부를 적은 Doxygen 주석을 함께 작성합니다.

### 2. RED 확인 — 반드시 실패를 직접 확인

**필수. 절대 생략하지 않습니다.**

```
python -m unittest <테스트모듈경로> -v
```

다음을 확인합니다.
- 테스트가 (에러가 아니라) **실패**하는가
- 실패 메시지가 기대와 일치하는가
- 기능이 없어서 실패하는 것이지, 오타 때문이 아닌가

테스트가 바로 통과한다면 이미 존재하는 동작을 테스트하고 있는 것입니다 — 테스트를 다시 씁니다. 테스트가 에러(exception)로 죽는다면 에러를 고치고 "실패"할 때까지 재실행합니다.

### 3. GREEN — 최소한의 구현

테스트를 통과시키는 가장 단순한 코드를 작성합니다. 테스트가 요구하지 않는 기능을 추가하거나, 다른 코드를 리팩터링하거나, 미리 "개선"하지 않습니다.

### 4. GREEN 확인 — 반드시 통과를 직접 확인

**필수.**

```
python -m unittest discover -s <테스트 디렉토리> -p "test_*.py" -v
```

다음을 확인합니다.
- 이 테스트가 통과하는가
- 기존 테스트들도 계속 통과하는가
- 출력이 깨끗한가(에러/경고 없음)

테스트가 실패하면 코드를 고칩니다(테스트를 고치지 않습니다). 다른 테스트가 깨지면 지금 바로 고칩니다.

### 5. REFACTOR — 정리

통과 상태에서만 진행합니다: 중복 제거, 이름 개선, 헬퍼 추출. 테스트는 계속 통과 상태를 유지합니다. 새 동작을 추가하지 않습니다. 매 리팩터링 후 전체 테스트를 다시 실행합니다.

리팩터링이 끝나면 **`coding` 스킬 §3의 품질 게이트**(라인수/복잡도/중복/주석비율/네이밍)를 실행합니다.

### 6. 반복

함수 계약(§0)의 모든 사전/사후조건·예외·경계값이 테스트로 커버될 때까지 1~5를 반복합니다.

## 테스트 함수 주석 규칙 (Doxygen 형식, 이 프로젝트 고유 요구사항)

모든 테스트 함수에 아래 형식의 Doxygen 스타일 주석을 작성합니다(`coding`의 `references/doxygen-comments.md` 태그 체계를 테스트 함수로 확장한 것).

```python
class TestSubmitForm(unittest.TestCase):
    ## @brief 이메일이 빈 문자열이면 폼 제출이 거부되는지 검증한다.
    # @technique 동등분할(Equivalence Partitioning) - 유효하지 않은 입력 클래스
    # @case Negative
    # @pre email이 빈 문자열("")로 주어진다.
    # @post submitForm이 error="Email required"를 반환한다.
    def test_rejectsEmptyEmail(self):
        result = submitForm({"email": ""})
        self.assertEqual(result["error"], "Email required")
```

필수 태그:
- `@brief`: 이 테스트가 무엇을 증명하는지 한 줄 요약(구현이 아니라 **의도한 동작**을 설명)
- `@technique`: `references/test-design-techniques.md`에서 고른 테스트 설계 기법(ISO 29119-4 기준) 이름
- `@case`: `Positive`(정상/기대 동작 검증) 또는 `Negative`(오류/예외/경계 위반 검증) 중 하나
- `@pre`/`@post`: 해당 테스트가 다루는 함수 계약의 사전/사후조건(있는 경우)

이 주석은 `coding` 스킬의 주석 비율 지표(≥20%) 계산에도 포함되지만, 비율을 채우려는 목적이 아니라 **테스트의 의도와 근거를 남기는 것**이 목적입니다.

## 좋은 테스트란

| 기준 | 좋은 예 | 나쁜 예 |
|---|---|---|
| 최소성 | 한 가지만 검증. 이름에 "그리고"가 필요하면 나눈다 | `test_validatesEmailAndDomainAndWhitespace` |
| 명확성 | 이름이 동작을 설명 | `test_case1` |
| 의도 표현 | 원하는 API/동작을 보여줌 | 코드가 무엇을 해야 하는지 알 수 없음 |

테스트를 작성/수정할 때는 `references/writing-good-tests.md`(테스트가 실제로 무엇을 검증해야 하는지, 모킹을 언제/어떻게 해야 하는지)를 반드시 함께 참고하세요.

## 흔한 합리화와 반박

| 변명 | 실제로는 |
|---|---|
| "너무 단순해서 테스트할 필요 없다" | 단순한 코드도 깨집니다. 테스트는 몇 초면 됩니다. |
| "나중에 테스트하겠다" | 나중에 쓴 테스트는 바로 통과해버려 아무것도 증명하지 못합니다. 잘못된 것을 테스트하거나, 구현을 테스트하거나, 경계 케이스를 놓치기 쉽습니다. |
| "이미 수동으로 테스트했다" | 수동 테스트는 커버리지 기록도, 재실행도 안 됩니다. "됐었다"는 "충분히 검증했다"가 아닙니다. |
| "지금 지우면 들인 시간이 아깝다" | 매몰비용 오류입니다. 신뢰할 수 없는 코드를 유지하는 것이 진짜 낭비입니다. |
| "참고용으로 남기고 테스트부터 쓰겠다" | 결국 그 코드에 맞춰 테스트를 쓰게 됩니다. 그건 사후 테스트입니다. |
| "테스트하기 어려운 건 설계 문제" | 맞습니다. 테스트하기 어렵다는 건 사용하기도 어렵다는 신호입니다 — 인터페이스를 단순화하세요. |

## 위험 신호 — 발견하면 즉시 중단하고 처음부터

- 테스트보다 코드가 먼저 존재함
- 테스트가 바로 통과함(실패를 본 적이 없음)
- 왜 실패했는지 설명할 수 없음
- "일단 이번만" 하는 합리화
- "이미 수동으로 확인했다" / "정신은 지켰으니 됐다"
- 기존 코드를 "참고"하거나 "적용"하겠다는 말

**이 경우 모두: 코드를 지우고 TDD로 다시 시작합니다.**

## 예시 — 버그 수정

**버그:** 빈 이메일이 통과되어버림

**RED**
```python
class TestSubmitForm(unittest.TestCase):
    ## @brief 이메일이 빈 문자열이면 폼 제출이 거부되는지 검증한다.
    # @technique 동등분할(Equivalence Partitioning) - 유효하지 않은 입력 클래스
    # @case Negative
    def test_rejectsEmptyEmail(self):
        result = submitForm({"email": ""})
        self.assertEqual(result["error"], "Email required")
```

**RED 확인**
```
$ python -m unittest test_form -v
FAIL: expected 'Email required', got None
```

**GREEN**
```python
def submitForm(formData):
    if not formData.get("email", "").strip():
        return {"error": "Email required"}
    # ...
```

**GREEN 확인**
```
$ python -m unittest discover -s tests -v
OK
```

**REFACTOR**: 여러 필드에 같은 검증이 필요하면 공통 검증 함수로 추출(`coding` 스킬 품질 게이트로 라인수/복잡도 확인).

## 완료 전 체크리스트

- [ ] 새로 추가/변경한 함수마다 테스트가 있는가
- [ ] 각 테스트가 구현 전에 실패하는 것을 직접 확인했는가
- [ ] 각 테스트가 예상된 이유로 실패했는가(기능 없음이지 오타가 아님)
- [ ] 각 테스트를 통과시키는 최소한의 코드만 작성했는가
- [ ] 전체 테스트가 통과하는가
- [ ] 출력이 깨끗한가(에러/경고 없음)
- [ ] 실제 코드를 검증하는가(모킹은 불가피한 경우만)
- [ ] 경계값과 오류 경로가 커버되는가
- [ ] 모든 테스트 함수에 `@brief`/`@technique`/`@case` Doxygen 주석이 있는가
- [ ] 긍정(Positive) 케이스와 부정(Negative) 케이스가 모두 존재하는가(하나만 있다면 누락된 쪽을 보고)
- [ ] `coding` 스킬의 품질 게이트를 통과했는가

체크박스를 다 채울 수 없다면 TDD를 건너뛴 것입니다 — 처음부터 다시 시작합니다.

## 막혔을 때

| 문제 | 해결 |
|---|---|
| 테스트를 어떻게 짤지 모르겠다 | 원하는 API를 먼저 써본다. 단언(assert)부터 작성한다. 사용자에게 물어본다. |
| 테스트가 너무 복잡하다 | 설계가 복잡한 것입니다. 인터페이스를 단순화하세요. |
| 모든 걸 모킹해야 한다 | 결합도가 너무 높은 것입니다. 의존성 주입을 사용하세요. |
| 테스트 준비(setup)가 거대하다 | 헬퍼로 추출하세요. 그래도 복잡하면 설계를 단순화하세요. |

## 디버깅과의 연계

버그를 발견하면 그 버그를 재현하는 실패하는 테스트부터 작성하고 TDD 사이클을 따릅니다. 그 테스트가 수정을 증명하고 회귀를 방지합니다. 테스트 없이 버그를 고치지 않습니다.

## 최종 규칙

```
프로덕션 코드 → 그에 대응하는 테스트가 존재했고, 먼저 실패했다
그렇지 않다면 → TDD가 아니다
```

사용자의 명시적 허락 없이는 예외를 두지 않습니다.
